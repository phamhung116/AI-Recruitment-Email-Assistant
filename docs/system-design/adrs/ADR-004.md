# ADR-004: DELIVERY_UNKNOWN Status Reconciliation & HR Manual Resolution Strategy

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

When an outbound transmission attempt to the Resend Email Provider API times out or suffers network connection drop during Phase B, the system cannot verify whether Resend accepted the email before dropping the connection. In accordance with Product Spec (`DEC-004`) and BA Requirements (`FR-007`, `AC-015`, `AC-016`), Phase C transitions the state to `DELIVERY_UNKNOWN`. How should the system handle status reconciliation and manual resolution?

## 2. Decision Drivers

- Safety mapping into `DELIVERY_UNKNOWN` on unconfirmed provider response during Phase B.
- Mandatory status verification prior to retry to prevent duplicate sends (`UC-006`).
- Full audit logging for manual HR status overrides (`AC-015`, `AC-016`).
- Provider capability findings documented in `SPIKE-001`.

## 3. Considered Options

- **Option 1 (Chosen)**: **Dual-Path Reconciliation (Provider-Backed Idempotent Replay within 24h + HR Manual Resolution Modal)**:
  - **Known Resend Email ID**: If the Resend email `{id}` is already known (from a previous non-timeout response), the system calls Resend GET `/emails/{id}` to fetch delivery status.
  - **Unknown Email ID (POST Timeout in Phase B)**: If the POST request timed out and the Resend email `{id}` is unknown, GET `/emails/{id}` cannot be called initially (Resend does not support querying GET by `operation_id`).
  - **Within 24-Hour Retention Window**: System executes provider-backed idempotent reconciliation by re-transmitting the exact payload with the exact same `Idempotency-Key` (`operation_id`). Resend returns the cached response (containing original `{id}` and status) without delivering a second email.
  - **After 24-Hour Retention Window**: Resend idempotency key cache expires. Automatic replay is strictly PROHIBITED after 24h; system retains `DELIVERY_UNKNOWN` state and requires HR manual resolution.
  - **HR Manual Resolution Dialog**: Displays human-readable guidance and explicit resolution choices ("Provider Accepted" vs "Provider Not Received") requiring explicit warning confirmation and writing Audit Log (`AC-015`, `AC-016`).
- **Option 2**: **Blind Automatic Retry** — Automatically retry request without status verification or idempotency guarantees.
- **Option 3**: **Infinite Block** — Block all retries permanently without manual override capability.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Dual-Path Reconciliation)**.

### Rationale:
1. **Safety First**: Option 2 (Blind Retry) risks physical duplicate email delivery. Re-using Resend's `Idempotency-Key` within 24h guarantees that Resend returns cached status without duplicate delivery.
2. **Human-in-the-Loop Governance**: When the 24-hour idempotency window has expired or provider status is un-reconcilable via API, HR Recruiter manual verification (`AC-015`, `AC-016`) provides an operational safety mechanism. HR checks external email logs/client, selects the verified outcome, acknowledges a high-visibility warning dialog, and logs an immutable audit event (`DELIVERY_UNKNOWN_RESOLVED_ACCEPTED` or `DELIVERY_UNKNOWN_RESOLVED_NOT_RECEIVED`).
3. **Controlled Retry Path**: Selecting "Provider Not Received" unlocks Retry Send using the SAME `Logical Send Operation ID` and creating `ProviderAttempt #2` in Phase A. Selecting "Provider Accepted" transitions state to `PROVIDER_ACCEPTED` and updates communicated outcome in Phase C.

## 5. Consequences

- **Positive Impacts**:
  - Prevents blind duplicate delivery while providing clear operational unblock paths.
  - Provider-backed idempotency guarantees zero duplicate delivery within 24h.
  - Full audit trail accountability for recruiter manual overrides.
- **Negative Impacts / Trade-offs**:
  - Requires manual HR intervention after 24 hours.

## 6. Security & Operability Impact

- Audit log records recruiter user ID, timestamp, rationale, and chosen resolution state for compliance auditing.

## 7. Traceability & Verification Approach

- **Verification Approach**: Mock integration tests simulating Phase B socket timeout, verifying provider-backed idempotent replay within 24h, and asserting Phase C manual override audit logging after 24h.
- **Downstream Owners**: Backend, Frontend, QA
