# ADR-001: Selection of Modular Monolith Target Architecture Style

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

The legacy prototype codebase contains an event-driven architecture comprising RabbitMQ message queues, Redis caching layers, Celery background worker tasks, and Transactional Outbox dispatchers. However, Product Specification v1.0.1 (`NG-001`) and Business Analysis Specification v1.2.0-BA (`GOAL-002`, `JOB-001`) explicitly limit MVP scope to single-candidate, recruiter-driven synchronous real-email delivery without background campaign batches or multi-candidate queues. Which architecture style best balances operational simplicity, data consistency, deterministic safety guard enforcement, and rapid MVP delivery?

## 2. Decision Drivers

- Strict single-candidate recruiter manual execution (`GOAL-002`, `JOB-001`).
- Operational simplicity and maintainability by a small engineering team (`CON-001`, `SIMPLICITY_BEFORE_SCALE`).
- Direct synchronous deterministic safety guard check before email provider transmission (`DRV-F-002`, `NFR-001`).
- Elimination of non-product background message brokers from MVP scope (`CON-003`).

## 3. Considered Options

- **Option 1 (Chosen)**: **Modular Monolith (FastAPI + React + PostgreSQL + Resend Email Provider Adapter)** — Single deployment unit with clear internal module boundaries (Rules Engine, Draft Service, 3-Phase Send Operation Service, Resend Provider Adapter, Audit Service).
- **Option 2**: **Monolith with Internal Background Queue Worker** — Retain an internal asynchronous task queue (e.g. ARQ / Celery) for provider requests.
- **Option 3**: **Full Event-Driven Architecture** — Retain legacy RabbitMQ, Redis, Celery workers, and Transactional Outbox dispatcher.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Modular Monolith)**.

### Rationale:
1. **MVP Alignment**: Product Spec (`NG-001`) and BA Spec (`GOAL-002`) mandate a single-candidate, recruiter-executed synchronous send flow. Adding background queues introduces unneeded eventual consistency, queue latency, and broker maintenance.
2. **Deterministic Safety**: Modular Monolith guarantees that deterministic checks (`rules.py`) execute synchronously in the API request path prior to initiating any Provider Attempt (`NFR-001`).
3. **Decoupled 3-Phase Transaction Boundary**: Phase A prepares and commits the DB transaction, Phase B calls the Resend HTTP API outside the DB transaction boundary, and Phase C finalizes the state and audit log atomically (`ADR-005`).

## 5. Consequences

- **Positive Impacts**:
  - Zero message broker infrastructure dependencies (no RabbitMQ/Redis/Celery needed for MVP).
  - Simple deployment and debugging topology.
  - Strict transactional consistency for audit logs and entity states.
- **Negative Impacts / Trade-offs**:
  - High-volume background campaign sending is not supported (explicitly out of MVP scope).

## 6. Security & Operability Impact

- Simplifies security boundary; all backend operations run within a single trusted FastAPI container.

## 7. Traceability & Verification Approach

- **Verification Approach**: Monolithic FastAPI API endpoint integration tests verifying synchronous request-response flow from import to provider transmission and audit logging.
- **Downstream Owners**: Backend, Architecture, DevOps, QA
