# ADR-006: Legacy Infrastructure Disposition & Scope Boundaries

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

The prototype repository contains legacy infrastructure services including RabbitMQ message broker, Redis cache, Celery worker tasks, Transactional Outbox dispatcher, and LLM semantic review code. However, Product Specification v1.0.1 (`NG-001`, `NG-002`) and BA Specification v1.2.0-BA explicitly scope the MVP to single-candidate, recruiter-executed synchronous send delivery without background campaign infrastructure or LLM blocking. How should these legacy components be disposed of in the target architecture?

## 2. Decision Drivers

- Product Scope Prohibitions (`NG-001` no automated campaign batches; `NG-002` no AI decision-making).
- Operational Simplicity (`CON-001`, `CON-003`).
- Single-candidate synchronous execution (`GOAL-002`, `JOB-001`).

## 3. Considered Options

- **Option 1 (Chosen)**: **Decommission Legacy Infrastructure from Core Flow**:
  - Remove RabbitMQ, Redis, and Celery services from `docker-compose.yml` (`CON-003`).
  - Decommission `outbox_dispatcher.py` (`ADR-006`).
  - Remove LLM calls from core send path (`NG-002`). LLM integration is relegated to an optional asynchronous advisory endpoint in `LATER`.
- **Option 2**: **Keep Infrastructure Containers Active** — Maintain brokers and workers running alongside the monolith even if unused.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Decommission Legacy Infrastructure)**.

### Rationale:
1. **Scope Compliance**: Product Spec (`NG-001`, `NG-002`) explicitly prohibits automated background campaigns and AI decision-making. Retaining unused message brokers violates `CON-001` (Operational Simplicity).
2. **Simplified Docker Setup**: Decommissioning brokers reduces local development and deployment requirements to just FastAPI app container + PostgreSQL 16 DB container.

## 5. Consequences

- **Positive Impacts**:
  - Dramatic reduction in infrastructure complexity, RAM usage, and startup time.
  - Zero queue latency or broker configuration overhead.
- **Negative Impacts / Trade-offs**:
  - If high-volume batch campaigns are ever added post-MVP, queuing infrastructure will need to be re-introduced under a separate architecture review.

## 6. Security & Operability Impact

- Reduces network attack surface by eliminating open ports for RabbitMQ (5672/15672) and Redis (6379).

## 7. Traceability & Verification Approach

- **Verification Approach**: Clean `docker-compose up -d` starting only PostgreSQL 16 and FastAPI app, running full test suite without broker connections.
- **Downstream Owners**: DevOps, Backend, QA
