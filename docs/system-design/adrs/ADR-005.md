# ADR-005: Decoupled Transaction Boundary (Phase A / Phase B / Phase C) & Immutable Audit Requirement

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

Product Goal `GOAL-003`, Capability `CAP-009`, and BA Requirements `FR-009`, `NFR-002` require that an action is considered complete ONLY when its corresponding audit log record is preserved in an append-only, immutable audit trail. Holding a database transaction open while waiting for an external HTTP API network response causes DB connection pool exhaustion and long-running locks. How should transaction boundaries be structured to guarantee audit immutability without holding open DB connections?

## 2. Decision Drivers

- Immutable append-only audit trail for candidate import, draft generation, safety guard checks, send operations, and decision corrections.
- Action completeness strictly tied to audit record persistence.
- Decoupled 3-Phase Execution Model to prevent DB connection pool starvation during external HTTP calls.

## 3. Considered Options

- **Option 1 (Chosen)**: **Decoupled 3-Phase Execution Model (Phase A DB Commit -> Phase B External HTTP -> Phase C DB Finalize)**:
  - **Phase A (Prepare & Lock in DB Transaction)**: Local DB transaction re-validates deterministic guard, creates or retrieves unique `LogicalSendOperation`, freezes `DraftRevision`, creates child `ProviderAttempt` in state `PREPARED` (binding `attempt_number` and `operation_id`), writes `SEND_ATTEMPT_PREPARED` audit event, and COMMITS local DB transaction immediately. Release DB connection back to pool.
  - **Phase B (External Outbound HTTP Call)**: Outbound HTTP REST request to Resend API executed completely outside DB transaction boundary (using `configurable provider timeout`, 10.0s default). Uses the existing `ProviderAttempt` created in Phase A. Do NOT create a `ProviderAttempt` after external call.
  - **Phase C (Finalize Local DB State & Atomic Audit)**: Finalize local DB transaction. Opens new DB connection to update existing `ProviderAttempt` (`ACCEPTED` / `FAILED` / `UNCONFIRMED`), update `LogicalSendOperation` status (`PROVIDER_ACCEPTED` / `DEFINITIVE_FAILURE` / `DELIVERY_UNKNOWN`), update candidate communicated decision ONLY IF provider returned `PROVIDER_ACCEPTED`, insert matching `AuditLog` entry, and COMMIT DB transaction atomically.
- **Option 2**: **Single Long-Running DB Transaction** — Hold DB connection open during external provider HTTP request.
- **Option 3**: **Asynchronous Background Outbox Queue** — Use external queue worker to decouple.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Decoupled 3-Phase Execution Model)**.

### Rationale:
1. **Connection Pool Safety**: Releasing DB connection at Phase A commit ensures that slow provider network calls during Phase B never hold DB locks or exhaust connection pools.
2. **Crash-Window Safety**: If the application crashes during Phase B, the DB state contains the `PREPARED`/`IN_FLIGHT` attempt record. On application restart, a crash-recovery task detects unfinalized operations older than recovery threshold and transitions them to `DELIVERY_UNKNOWN` via a local state transition with audit log.
3. **Atomic Phase C Finalization**: Phase C executes status update and `audit_logs` row insertion inside a single atomic DB transaction block. If audit insertion fails, Phase C rolls back, preventing orphaned state changes.

## 5. Consequences

- **Positive Impacts**:
  - High DB connection pool throughput.
  - 100% guarantee that no state finalization occurs without a matching audit log entry.
- **Negative Impacts / Trade-offs**:
  - Requires crash-recovery check for operations left in `SENDING_UNCONFIRMED` if app terminates during Phase B.

## 6. Security & Operability Impact

- Database roles configured to grant `INSERT` and `SELECT` only on `audit_logs` table.

## 7. Traceability & Verification Approach

- **Verification Approach**: Integration test executing Phase A commit, asserting DB connection released during Phase B, and verifying Phase C atomic status + audit log commit.
- **Downstream Owners**: Database, Backend, QA
