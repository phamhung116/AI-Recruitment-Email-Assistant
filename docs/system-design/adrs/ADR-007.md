# ADR-007: Strangler-Fig Migration Strategy from Legacy Prototype Monolith to Minimal Real-Email MVP

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

The repository currently contains a prototype monolith backend where `email_workflow.py` holds 350+ lines of mixed simulation logic, route handlers, and outbox polling. To migrate to the Modular Monolith target architecture safely without breaking existing REST contracts, how should module refactoring and migration be executed?

## 2. Decision Drivers

- Maintain existing API endpoint paths (`/candidates`, `/email-drafts`, `/audit-logs`) to avoid breaking frontend contracts.
- Modularize backend into clear single-responsibility services (`rules.py`, `draft_service.py`, `send_service.py`, `provider_adapter.py`, `audit.py`).
- Zero downtime / zero breaking changes during refactoring.

## 3. Considered Options

- **Option 1 (Chosen)**: **In-Place Strangler-Fig Refactoring**:
  - Phase 1: Modularize `rules.py` and `audit.py` to enforce Phase C transaction inclusion (`ADR-005`).
  - Phase 2: Create `draft_service.py` for template rendering and Draft Revision tracking (`ADR-003`).
  - Phase 3: Create `send_service.py` executing 3-Phase Logical Send Operations and Provider Attempts (`ADR-003`, `ADR-005`).
  - Phase 4: Create `provider_adapter.py` integrating Resend REST API (`ADR-002`).
  - Phase 5: Decommission legacy queue polling in `email_workflow.py` and broker containers in `docker-compose.yml` (`ADR-006`).
- **Option 2**: **Greenfield Re-write in New Repository** — Discard existing codebase and rewrite from scratch.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (In-Place Strangler-Fig Refactoring)**.

### Rationale:
1. **Preserves Existing Work**: Retains working Excel import (`excelImport.py`), candidate ORM models, frontend components, and routing patterns while replacing the simulated send path with the real Resend provider 3-Phase pipeline.
2. **Low Risk**: Enables incremental component-by-component verification.

## 5. Consequences

- **Positive Impacts**:
  - Low migration risk; existing frontend pages continue working seamlessly.
- **Negative Impacts / Trade-offs**:
  - Requires maintaining backward-compatible schema models during intermediate refactoring steps.

## 6. Security & Operability Impact

- Guarantees continuous audit trail continuity throughout the migration phase.

## 7. Traceability & Verification Approach

- **Verification Approach**: Integration test suite verifying that API requests produce identical response schemas while using the new 3-Phase real-email provider pipeline.
- **Downstream Owners**: Backend, Database, Frontend, QA
