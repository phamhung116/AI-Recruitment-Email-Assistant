# ADR-003: Logical Send Operation, Provider Attempts, and Idempotent Retry Identity

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

Product Decision `DEC-004` and BA Requirements `FR-005`, `NFR-003` dictate that double-clicks, browser reloads, or network timeouts must never produce multiple Logical Send Operations for the same Draft Revision. How should the system structure the relationship between Draft Revisions, Logical Send Operations, and Provider Attempts to enforce anti-duplicate guarantees without masking network failures?

## 2. Decision Drivers

- Logical Send Operation creation freezing active draft; at most one Logical Send Operation per Draft Revision (`BR-013`).
- Retries reuse existing operation identity, recording multiple Provider Attempts (`BR-013`, `BR-015`).
- System-level anti-duplicate enforcement against double-click and page reload (`AC-003`, `AC-007`).
- Decoupled 3-Phase Transaction Boundary (Phase A DB Commit / Phase B Outbound HTTP / Phase C DB Finalize).

## 3. Considered Options

- **Option 1 (Chosen)**: **Explicit Entity Hierarchy (Draft Revision 1 : 1 Logical Send Operation 1 : N Provider Attempts)** — Single DB unique constraint `(draft_revision_id)` on `Logical Send Operation`, with a child table `Provider Attempt` tracking each physical outbound HTTP attempt (attempt sequence, timestamp, HTTP status, request payload digest, provider reference ID).
- **Option 2**: **Single Flat Record** — Overwrite attempt fields directly on the send operation record without preserving individual attempt histories.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Explicit Entity Hierarchy)**.

### Rationale:
1. **Strict 1:1 Invariant**: Placing a `UNIQUE` index on `logical_send_operation.draft_revision_id` guarantees at the database level during Phase A that no second operation can ever be inserted for the same revision, even if two concurrent requests hit the API simultaneously.
2. **Synchronized 3-Phase Attempt Lifecycle**:
   - **Phase A**: Local DB transaction re-validates deterministic guard, creates or retrieves unique `LogicalSendOperation`, freezes `DraftRevision`, creates a child `ProviderAttempt` in state `PREPARED` (attaching `attempt_number: N` and `operation_id`), writes `SEND_ATTEMPT_PREPARED` audit event, and COMMITS local DB transaction immediately.
   - **Phase B**: Transmits outbound HTTP request using the `PREPARED` `ProviderAttempt` outside DB transaction. Do NOT create a `ProviderAttempt` after external call has already occurred.
   - **Phase C**: Local DB transaction updates the existing `ProviderAttempt` record (`ACCEPTED` / `FAILED` / `UNCONFIRMED`), updates `LogicalSendOperation` status, updates candidate communicated decision ONLY IF provider returned `PROVIDER_ACCEPTED`, writes corresponding audit event, and COMMITS DB transaction atomically.
3. **Multi-Attempt Identity Retention**: Every HTTP transmission or reconciliation request creates its own distinct `ProviderAttempt` record (e.g. attempt #1 for initial send, attempt #2 for retry), but ALL attempts belong to the SAME `LogicalSendOperation` and reuse the SAME `operation_id` as the `Idempotency-Key` sent to Resend.

## 5. Consequences

- **Positive Impacts**:
  - Complete operational visibility into retry attempts and latency.
  - Zero duplicate operation creation on double-click or network retry.
- **Negative Impacts / Trade-offs**:
  - Requires maintaining child `provider_attempt` table records.

## 6. Security & Operability Impact

- Prevents race conditions and double-send bugs caused by rapid user interface interactions.

## 7. Traceability & Verification Approach

- **Verification Approach**: Concurrent request test firing 10 parallel HTTP POST requests to `/api/v1/email-drafts/{id}/send`, verifying exactly 1 Phase A operation is created and committed.
- **Downstream Owners**: Backend, Database, QA
