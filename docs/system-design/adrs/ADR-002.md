# ADR-002: Email Provider Adapter & Response Normalization Strategy (ADI-001)

- **Status**: accepted
- **Date**: 2026-08-12
- **User Approval Date**: 2026-08-12
- **Author**: Principal System Software Architect
- **Superseded By**: N/A

## 1. Context & Problem Statement

Product Decision Input `ADI-001` asks: What Email Provider integration model (Synchronous HTTP vs Asynchronous Webhook/Polling) should be selected to normalize provider transmission results into `PROVIDER_ACCEPTED`, `DEFINITIVE_FAILURE`, and `DELIVERY_UNKNOWN`? How should the architecture handle idempotency headers, provider deduplication, and status reconciliation?

## 2. Decision Drivers

- Real single-candidate email delivery execution (`CAP-006`).
- Strict outcome normalization into 3 states: `PROVIDER_ACCEPTED`, `DEFINITIVE_FAILURE`, and `DELIVERY_UNKNOWN` (`DEC-004`).
- Decoupled 3-Phase Execution Model (Phase A DB Commit -> Phase B External HTTP -> Phase C DB Finalize).
- Idempotent transmission mapping and residual provider duplicate delivery risk management.

## 3. Considered Options

- **Option 1 (Chosen)**: **Synchronous HTTP REST Email Provider Adapter (Resend API)** — Outbound HTTPS POST to Resend API (`POST /emails`) executed during Phase B (outside DB transaction) using configurable provider timeout (10.0s default). Standardizes provider payload with `Idempotency-Key` header set to `Logical Send Operation ID`.
- **Option 2**: **SendGrid v3 Mail Send Integration** — HTTPS POST to SendGrid `/v3/mail/send` (HTTP 202 Accepted, lacks native idempotency header).
- **Option 3**: **Postmark Send Email Integration** — HTTPS POST to Postmark `/email`.

## 4. Decision Outcome & Rationale

Chosen Option: **Option 1 (Resend API Integration)**.

### Rationale:
1. **User Selection & Spike Verification**: Technical spike `SPIKE-001` evaluated provider capabilities, and Resend was selected by User on 2026-08-12.
2. **Native Idempotency Support**: Resend supports passing `Idempotency-Key: op_<uuid>` header on POST `/emails` with a 24-hour deduplication retention window (`DEC-004`).
3. **Provider-Backed Idempotent Replay (Within 24 Hours)**: When a Phase B HTTP POST request times out and the response containing Resend's email ID is lost, Resend GET `/emails/{id}` cannot be called initially because `{id}` is unknown (Resend GET endpoint does not support querying by `operation_id`). Within 24 hours, the system executes provider-backed idempotent reconciliation by re-transmitting the exact payload with the exact same `Idempotency-Key` (`operation_id`). Resend returns the cached response containing original `{id}` and status without sending a duplicate email.
4. **Expired Retention Window (> 24 Hours)**: After 24 hours, Resend's idempotency key cache expires. Automatic replay is strictly PROHIBITED after 24h; the system retains `DELIVERY_UNKNOWN` state and requires HR manual resolution (`ADR-004`).
5. **Synchronous Result Normalization**:
   - **HTTP 200/201** -> `PROVIDER_ACCEPTED`. Resend message ID `{ "id": "49bf7438-e70d-4208-88d4-6d97c555f8b1" }` recorded; draft status set to `PROVIDER_ACCEPTED`; communicated outcome updated.
   - **HTTP 4xx (400, 422)** -> `DEFINITIVE_FAILURE` (Content / Address Validation Failure). Operation transitions to `FAILED_TERMINAL`. Requires HR editing editable draft content or recipient email, creating a new `Draft Revision`.
   - **HTTP 5xx (500, 503)** -> `DEFINITIVE_FAILURE` (Transient / Retryable Failure). Operation remains in `DEFINITIVE_FAILURE`. Retrying reuses the same `Logical Send Operation ID` and idempotency key.
   - **Socket Timeout / Network Drop** -> `DELIVERY_UNKNOWN`. Re-sending within 24h uses provider-backed idempotent replay.

## 5. Consequences

- **Positive Impacts**:
  - Zero requirement for public domain DNS, SSL ingress, or webhook endpoints.
  - Native provider deduplication via `Idempotency-Key` header (24h window).
  - Clear, deterministic mapping from HTTP status codes to system states.
- **Negative Impacts / Trade-offs**:
  - Demo limitation: `onboarding@resend.dev` delivers only to the registered Resend account email; sending to external candidates/mentors requires custom DNS domain verification.

## 6. Security & Operability Impact

- Provider API credential stored in server environment variable `RESEND_API_KEY`, never exposed to browser or recorded in application logs.
- **Backend-side rate/quota error normalization, operational metrics and human-readable guidance**: Backend owns and enforces Resend free-tier quota limits (3,000 emails/month, 100 emails/day) and translates provider rate-limit responses into operational metrics and human-readable HR guidance. Frontend does not own or decide authoritative quota logic.

## 7. Traceability & Verification Approach

- **Verification Approach**: Mock Provider Adapter unit tests simulating 200 OK, 422 Validation Error, 503 Transient Error, and ConnectTimeout exceptions during Phase B, asserting Phase C exact status state transitions.
- **Downstream Owners**: Backend, Architecture, QA
